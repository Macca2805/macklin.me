> Every example in this post compiles. None of them produce a warning. All of them pass `go vet`. And every one of them quietly does something other than what the person who wrote it meant. This post is a collection of **Go** footguns I've watched land in real pull requests over the last few weeks, each with the smallest example I could write and the fix.

# Context

In my post on [immutability in Go](/immutability-in-go) I showed that assigning a slice to a new variable doesn't copy the data underneath it. I thought I understood that pretty well. Then I spent a few weeks reviewing a lot of **Go** written by a mix of people and AI coding agents, and the same family of bugs kept turning up in slightly different clothes.

They fall into two groups.

1. **Sharing when you thought you copied.** You hold on to something, and someone else changes it under you.
2. **Comparing when you thought you checked.** You write `==` or `!= nil`, and **Go** compares something other than what you had in mind.

None of these are new. Most are covered somewhere in the Go FAQ or a blog post from 2015. But knowing about them and spotting them in a 600 line diff are two different skills.

> ℹ️ Each example links to the **Go Playground** so you can run it yourself. They're deliberately tiny, so read the output before you read the explanation and see if you can spot it first.

# Part 1: Sharing When You Thought You Copied

## Two Names, One Map

Let's start with an easy one.

```go
func main() {
    defaults := map[string]int{"retries": 3}
    settings := defaults

    settings["retries"] = 5

    fmt.Println("defaults =", defaults)
    fmt.Println("settings =", settings)
}

// Output:
// defaults = map[retries:5]
// settings = map[retries:5]
```

[Run in Go Playground ↗](https://go.dev/play/p/t557RSA4HmQ)

A map value in **Go** is a small header pointing at the real data. Assigning it to a new variable copies the header, so `defaults` and `settings` are two names for the same map. Change one and you've changed both.

The version I actually saw in a pull request was two package level variables built from the same map literal, one of which was later modified at startup. Every test passed because no test checked the other variable.

The fix is to say you want a copy.

```go
settings := maps.Clone(defaults)

// Output:
// defaults = map[retries:3]
// settings = map[retries:5]
```

[Run in Go Playground ↗](https://go.dev/play/p/QenbNi-tfT2)

> ℹ️ `maps.Clone` is a **shallow** copy. If your map values are themselves maps, slices or pointers, those are still shared.

## The Subslice That Leaks Its Tail

This one is subtle enough that it survived local testing, CI and a human review.

```go
var scores = []int{90, 80, 70, 60}

func topTwo() []int {
    return scores[:2]
}

func main() {
    mine := topTwo()
    mine = append(mine, 100)

    fmt.Println("mine   =", mine)
    fmt.Println("scores =", scores)
}

// Output:
// mine   = [90 80 100]
// scores = [90 80 100 60]
```

[Run in Go Playground ↗](https://go.dev/play/p/c44HEcp_vGb)

The caller never touched `scores`, and yet `70` is gone.

A slice has three parts: a pointer to an array, a length, and a **capacity**. `scores[:2]` has a length of 2 but a capacity of 4, because there are still two elements left in the array after it. When the caller appends, `append` sees there is spare capacity and writes straight into it. That spare capacity is the rest of `scores`.

In the real code, `scores` was a cache shared across requests. One request appending to its result would corrupt the answer for the next request. Under a single request in a test it looked perfect.

The fix is a single character, using the three index slice expression to clamp the capacity.

```go
func topTwo() []int {
    return scores[:2:2]
}

// Output:
// mine   = [90 80 100]
// scores = [90 80 70 60]
```

[Run in Go Playground ↗](https://go.dev/play/p/ZG7qMLohOqL)

`scores[:2:2]` means "elements 0 to 2, with a capacity of 2". Now there is no spare room, so `append` has to allocate a new array and leaves `scores` alone.

## The Buffer That Gets Reused

The standard library has a few performance options that trade safety for fewer allocations. `csv.Reader.ReuseRecord` is one of them.

```go
func main() {
    r := csv.NewReader(strings.NewReader("alice,1\nbob,2\n"))
    r.ReuseRecord = true

    var rows [][]string
    for {
        row, err := r.Read()
        if err != nil {
            break
        }
        rows = append(rows, row)
    }

    fmt.Println(rows)
}

// Output:
// [[bob 2] [bob 2]]
```

[Run in Go Playground ↗](https://go.dev/play/p/8pTlOLhhDb9)

Where did Alice go?

With `ReuseRecord` turned on, every call to `Read` returns the **same** backing slice with new contents. Storing it stores a reference to a buffer that the next `Read` overwrites. By the end, every row in `rows` points at the same buffer, which holds whatever was read last.

The real version of this was a streaming join over a file several gigabytes in size. With a small input it was fine, because the bug only shows up once you keep a row past the next read. With the real input the output was quietly wrong.

If you want to keep the row, copy it.

```go
rows = append(rows, slices.Clone(row))

// Output:
// [[alice 1] [bob 2]]
```

[Run in Go Playground ↗](https://go.dev/play/p/veQo0T6Wztr)

Or just don't turn on `ReuseRecord` unless a profiler has told you to.

## The Rule for Part 1

**If you keep it past the moment you got it, clone it.** That covers maps, slices you got from someone else, and buffers from the standard library. `maps.Clone`, `slices.Clone` and `x[:n:n]` are your friends.

# Part 2: Comparing When You Thought You Checked

## `==` on a Struct With Pointers

**Go** lets you compare structs with `==` as long as every field is comparable. Pointers are comparable. So this compiles.

```go
type Person struct {
    Name  *string
    Email *string
}

func str(s string) *string { return &s }

func main() {
    a := Person{Name: str("Alice"), Email: str("alice@example.com")}
    b := Person{Name: str("Alice"), Email: str("alice@example.com")}

    fmt.Println("a == b:", a == b)
}

// Output:
// a == b: false
```

[Run in Go Playground ↗](https://go.dev/play/p/yC3dU5mVjI6)

Same name, same email, not equal. `==` compares each field, and each field is a pointer, so it compares **addresses**. `a.Name` and `b.Name` point to two different strings that happen to say the same thing.

The pointers were there for a good reason. The author needed to tell "not provided" apart from "provided as an empty string". The comparison was used as a guard: "if nothing changed, skip the update". Because it compared addresses, it never saw two values as equal, so the guard never fired and every update went through.

The fix is to say what you mean by equal. Yes, this is the same `Equals()` trick from [the immutability post](/immutability-in-go). I'm as surprised as you are.

```go
func equal(a, b *string) bool {
    if a == nil || b == nil {
        return a == b
    }
    return *a == *b
}

func (p Person) Equals(o Person) bool {
    return equal(p.Name, o.Name) && equal(p.Email, o.Email)
}

// Output:
// a == b: false
// a.Equals(b): true
```

[Run in Go Playground ↗](https://go.dev/play/p/AU9ClHCz0Dd)

## The Nil That Isn't Nil

This is the most famous one on the list, and it still gets everyone eventually.

```go
type Verifier interface {
    Verify() bool
}

type emailVerifier struct{}

func (v *emailVerifier) Verify() bool { return true }

func newVerifier(enabled bool) Verifier {
    var v *emailVerifier
    if enabled {
        v = &emailVerifier{}
    }
    return v
}

func main() {
    v := newVerifier(false)
    fmt.Println("v == nil:", v == nil)
    fmt.Printf("v = (%T, %v)\n", v, v)
}

// Output:
// v == nil: false
// v = (*main.emailVerifier, <nil>)
```

[Run in Go Playground ↗](https://go.dev/play/p/IwXr81gHUyZ)

An interface value in **Go** is a pair: a **type** and a **value**. It's only `nil` when both halves are `nil`.

`newVerifier(false)` returns a `nil` pointer, but the function's return type is `Verifier`, so **Go** wraps it in an interface whose type half is `*emailVerifier`. The value half is `nil`. The type half isn't. So `v == nil` is `false`, the caller's nil check passes, and the next line calls a method on a pointer that is, in fact, nil.

The fix is to return a bare `nil` from any function whose return type is an interface.

```go
func newVerifier(enabled bool) Verifier {
    if !enabled {
        return nil
    }
    return &emailVerifier{}
}

// Output:
// v == nil: true
```

[Run in Go Playground ↗](https://go.dev/play/p/SusCSoSyyTQ)

> ℹ️ The [Go FAQ](https://go.dev/doc/faq#nil_error) has a whole entry on this, and it's worth reading. The question I ask in review is simple: does every `return nil` in this function return the literal `nil`, or a typed variable that happens to be nil?

## `errors.As` and Embedding

This one surprised me, because embedding feels like it should just work.

```go
type NotFoundError struct{ ID string }

func (e NotFoundError) Error() string { return "not found: " + e.ID }

type QueryError struct {
    NotFoundError
    Query string
}

func main() {
    var err error = QueryError{NotFoundError{"42"}, "SELECT ..."}

    var target NotFoundError
    fmt.Println("errors.As:", errors.As(err, &target))
    fmt.Println("err:", err)
}

// Output:
// errors.As: false
// err: not found: 42
```

[Run in Go Playground ↗](https://go.dev/play/p/MNok-63KyjH)

`QueryError` embeds `NotFoundError`. It even prints like one, because the embedded `Error()` method is promoted. But `errors.As` doesn't look at what a type embeds. It walks the chain of errors returned by `Unwrap()` and checks the type of each one. `QueryError` has no `Unwrap()`, so the chain is one link long, and that link is a `QueryError`.

If you want `errors.As` to find it, put it in the chain.

```go
func (e QueryError) Unwrap() error { return e.NotFoundError }

// Output:
// errors.As: true
// target.ID: 42
```

[Run in Go Playground ↗](https://go.dev/play/p/LLbLjeKtB9p)

The person who wrote the original code had written a test for this case, and the test caught it before it shipped. That's the happy ending, and the reason I'd always write the test.

## Zero, or Missing?

The last one is less about an operator and more about what a zero value can't tell you.

```go
type Order struct {
    ID       string `json:"id"`
    Discount int    `json:"discount"`
}

func main() {
    var a, b Order
    json.Unmarshal([]byte(`{"id":"a","discount":0}`), &a)
    json.Unmarshal([]byte(`{"id":"b"}`), &b)

    fmt.Println("a.Discount =", a.Discount)
    fmt.Println("b.Discount =", b.Discount)
}

// Output:
// a.Discount = 0
// b.Discount = 0
```

[Run in Go Playground ↗](https://go.dev/play/p/qP2-ioDraWu)

Order `a` has a discount of zero. Order `b` doesn't have a discount field at all. After unmarshalling you can't tell them apart.

Most of the time that's fine. It stops being fine when you add a new field to a type that is already stored as JSON somewhere. Every record written **before** the field existed will unmarshal to `0`, and if `0` means something, every old record now claims that thing. In the case I saw, a new counter was read by a consumer as "zero means nothing new happened". Every historical record would have reported zero, when in reality the field just hadn't been invented when they were written.

If "missing" and "zero" need to mean different things, use a type that can say so.

```go
type Order struct {
    ID       string `json:"id"`
    Discount *int   `json:"discount"`
}

// Output:
// a.Discount = 0
// b.Discount == nil: true
```

[Run in Go Playground ↗](https://go.dev/play/p/p5JG_oXumSz)

## The Rule for Part 2

**On anything that isn't a plain number or string, `==`, `!= nil` and `errors.As` compare the container, not the contents.** Before you write one, ask yourself what the container is, and whether that's really what you want compared.

# Why These Keep Happening

I don't think any of these are **Go** being badly designed. Each one has a sensible reason behind it: cheap copies, no hidden allocations, a simple and predictable interface representation. The language does exactly what it says it will.

The trouble is that each example looks correct. They read like the code you meant to write. That makes them hard to catch in review, and almost impossible to catch with a small, single threaded unit test.

A few things I've found genuinely help:

- **Test the caller, not just the function.** For the subslice bug, a test that only checked `len(topTwo())` would pass. A test that appends to the result and then reads the original would fail.
- **Test with realistic input.** The CSV bug needed more than one row. Plenty of real bugs need more than one request at a time.
- **Pay attention to AI review comments on these specific shapes.** I'm not usually one to trust an automated reviewer, but on this family of bugs it was right far more often than it was wrong. Most of the examples in this post were first flagged by one.

The only recommendation I will make is the same one I gave last time. Take the time to learn and understand the language you are working with, including the parts that compile without complaint.
